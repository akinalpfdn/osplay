# Phase 025 (TAB-05) — Android over a USB cable through Android Open Accessory
Status: DONE

DEVPLAN reference: Phase 15 (part TAB-05). Depends on: PHASE-024 (TAB-04).

## Goal
An Android 12+ phone or tablet works as a display for a Mac or a PC over a USB cable, with no network, tethering or developer options, the way the iPad does over usbmuxd.

## Tasks
- [x] Research first (Mac done; the PC waits for an experiment, see the decisions below): binding WinUSB to the accessory-mode device (18D1:2D00/2D01) on Windows — a signed driver package in the installer or another route — and how the helper or installer installs it. Present the options to the user before building.
- [x] Core (each platform's USB API instead of libusb, user decision): the computer side — find Android devices, switch them to accessory mode (AOA control requests with Osplay's manufacturer, model and version strings), open the bulk endpoints and carry stream link records over them; a watcher that reports attached and detached devices like the usbmuxd one.
- [x] Android: Osplay as a USB accessory (accessory filter, the system's "open Osplay" prompt), the viewer session over the accessory's streams, a "USB cable" choice on the home screen like the iPad's.
- [x] Mac: start a host session on an attached accessory like the iPad USB flow; no reconnect after a disconnect from either side.
- [x] PC engine: find phone-like devices (MTP/PTP/ADB on Windows), send the switch through UsbDk, open the accessory through WinUSB as a byte pipe; report a device with USB debugging on (18D1:2D01).
- [x] PC engine C API and panel: Android devices on the cable as in the iPad USB flow, switched automatically while sharing; a warning for USB debugging.
- [x] PC installer and helper: ship UsbDk; bind WinUSB to 18D1:2D00 with a per-machine self-signed driver package. (The installer does it all; the helper needed no change.)
- [x] Keep USB tethering as a phone ↔ PC fallback; update the Android hint once AOA works.
- [x] Tests: core tests with in-memory and file-descriptor pipes, Android view model, CoreBridge; TESTING.md cases for Mac → Android and PC → Android over the cable, unplug and disconnect.
- [x] Docs: ARCHITECTURE, TESTING, TROUBLESHOOTING, PROTOCOL, DECISIONS (no libusb, so nothing for BUILDING or THIRD_PARTY).

## Acceptance Criteria
- [x] Mac → Android and PC → Android over a USB cable with no network, tethering or developer options (tested on a Galaxy S23; user decision 2026-10-31: no separate tablet test).
- [x] Unplugging ends the session within 10 s; nothing reconnects until the user chooses the cable again.

## Decisions Made This Phase
(append as you go; full entries go to DECISIONS.md)
- 2026-10-27 — User decision: add AOA after TAB-04. TAB-03 used USB tethering because it needed no code, but it reaches only a PC (macOS has no driver for Android tethering) and only devices with a tethering menu; Wi-Fi-only tablets usually have none.
- 2026-10-28 — User decision: Android side and Mac → Android first; the PC waits for an experiment on the PC (does the device switch to accessory mode, does Windows bind WinUSB to the accessory interface by itself). Windows blocks both steps today: Windows' MTP driver holds the device, so the AOA control requests cannot be sent without replacing its driver; self-signed WinUSB catalogs (libwdi) are reported to fail on Windows 11; an attestation-signed INF needs an EV certificate and still does not solve the first step; UsbDk filters every USB device. Each platform's own USB API (IOUSBHost on the Mac, WinUSB on Windows) instead of libusb: the AOA handshake and link records stay in the core, without an LGPL dependency.
- 2026-10-29 — Mac experiment with a Samsung (04e8:6860, "charging only"): IOUSBHostDevice opens without seizing although AppleUSBACM holds two interfaces; GET_PROTOCOL returns 2; after START the device comes back as 18d1:2d01 (2d00 without USB debugging) with two 512-byte bulk endpoints on interface 0. macOS asks once per new USB identity ("Allow accessory to connect?"); until the user allows it the device is not registered and Android drops back to normal mode after its 10 s accessory timeout, so the host switches again. Bulk OUT and IN time out while no app reads, so the host can wait for the viewer's first bytes.
- 2026-10-29 — User decision: while the Mac/PC shares, an Android device plugged in is switched to accessory mode automatically; Android's own "Open Osplay?" prompt starts the session. After a disconnect nothing reconnects by itself; the Android "computer on the USB cable" row starts it again.
- 2026-10-29 — Mac → Android tested by the user on a Galaxy S23 (U7–U9 and rotation): works. Found and fixed on the device: the accessory read ignores zero-length packets and a pulled cable (now interrupted with a signal), and adb's exclusive hold blocked the switch (now through IOKit's device interface). Remaining: the PC experiment, then the PC side or a decision without it.
- 2026-10-30 — PC experiment and user decisions: UsbDk sends the switch with USB debugging off, WinUSB on 18D1:2D00 opens the accessory; the installer binds WinUSB with a self-signed package; USB debugging on (2D01) is not supported on the cable and gets a warning (DECISIONS.md).
- 2026-10-30 — PC engine tested on the S23 with OsplayAndroidTest (Zadig's WinUSB binding standing in for the installer's): switched, the stored pairing was used, streaming; unplugging closed the session (NETWORK) and removed the virtual monitor. The helper serves one client, so the tray app must be closed while the tool runs.
- 2026-10-30 — A device with USB debugging on shows an ADB interface in its normal mode, so the PC no longer switches it (no "Open Osplay?" prompt, adb not interrupted) and only warns. Panel tested by the user on the S23: cable session, unplug, and the debugging warning all work. Only a Samsung tested so far.
- 2026-10-30 — User decision: count only unanswered switches; an opened accessory resets its device's count (PC and Mac). PC tested on the S23: five plug-ins in one sharing session, all connected. Mac change not compiled yet (no Mac here): CI and a Mac test.
- 2026-10-31 — Installer: the accessory driver is signed at install time with PowerShell (New-FileCatalog, probed on the PC: accepted, and Windows bound it after Zadig's package was removed; DECISIONS.md). UsbDk sees almost no device until Windows restarts once (its MSI returns 0). User decision: no restart prompt; the finished page says the cable works after one restart, everything else works at once.
- 2026-10-31 — Installer tested on the PC (UsbDk and Zadig removed first): UsbDk and the accessory driver installed, one certificate without a private key; after one restart U11 (cable) and Wi-Fi worked. The "Start with Windows" entry pointed at a stale development build, which started after the restart: the installer now repoints an existing entry at the installed Osplay.exe (user decision), and the stale folder was deleted. Remaining: U14 (uninstall, reinstall with the finished-page note).
- 2026-10-31 — U14 on the PC: the uninstaller removed UsbDk (Osplay's copy), the accessory package, the certificate, the app, service and firewall rule; UsbDk's class filter was gone, so no USB risk at the next restart. UsbDk's uninstaller keeps its service registered and its driver running until a restart: installing again before that fails with 1603, now shown as a finished-page note (user decision: rare, a restart and another run is acceptable); verified. The finished-page notes were clipped by the label's fixed height; fixed and verified. UsbDk's own "Please restart your computer" box appears even with /qn: now passed MSGBOX=n (UsbDk's documented switch, from its source). User decision: not verified on the PC (would need another uninstall and restart); check it at the next clean install.
- 2026-10-31 — User decision: TAB-05 is done without a tablet test. AOA is the same on a phone and a tablet, and the cable needs no tethering or hotspot, so the S23 results stand for tablets. The Mac half of the unanswered-switch fix (c236393) compiles on the Mac.
